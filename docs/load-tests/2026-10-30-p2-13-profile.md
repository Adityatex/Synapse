# P2-13 follow-up: what the latency creep is

**Date:** 2026-10-30. **Where:** the same laptop as `2026-10-26-p2-13-local.md`; collab built from `main` after P2-14 and P2-15 (Hocuspocus 4.7.1), plus the load test from the P2-13 branch. Plan: `p2-13-profiling-plan.md`.

## Answer

The creep is **not** the document growing and **not** the load generator. It comes from how the replicas keep each other in sync through Redis: on every change, a replica publishes its state vector (a Yjs *SyncStep1*), and every other replica answers with `encodeStateAsUpdate(doc, thatStateVector)`. Even when the asking replica is already up to date, that reply carries the document's **whole delete set**, and the asker decodes and applies all of it. Its size is the number of deleted ranges the document has accumulated, which only grows. Cost per edit therefore grows with the room's edit history, and with two replicas the busy time of each rose from 35% to 88% of a core in ten minutes, which is queueing delay.

With one replica this path is not taken, and the creep does not appear.

## The three runs

Each: 10 minutes, 10 editors a room, 5 edits/s each, 15 s warm-up, V8 CPU profile (1 ms sampling, over the inspector) of two 2-minute windows: seconds 20 to 140 ("early") and 470 to 590 ("late").

| run | edits/s | p95 minute 0 → minute 9 | p50 minute 0 → minute 9 | server busy, early → late | memory (rss) |
|---|---|---|---|---|---|
| 1 room, 1 replica | 43 | 5.2 → 7.0 ms | 2.7 → 2.5 ms | 5.7% → 5.3% | 121 → 154 MB, x1.02 |
| 5 rooms, 1 replica | 217 | 7.2 → 8.0 ms | 3.7 → 3.0 ms | 22.8% → 24.7% | 130 → 181 MB, x1.20 |
| 5 rooms, **2 replicas** | 218 | **9.8 → 72.4 ms** (worker 1) | 4.8 → 22.8 ms | **34.9% → 88.2%** (both replicas) | 143 → 190 MB, x1.25 / x1.19 |

(The third row repeats the shape of the 2026-10-26 run: p95 6 → 48 ms there, 10 → 72 ms here. So the creep reproduces. This run was a little worse, which I put down to the profiler being attached, and to both replicas starting fresh; I did not test either.)

Docker's CPU figure for the same runs: one replica 11% (1 room) and 32% (5 rooms) on average; **two replicas 70% each**. The same 218 edits a second cost about 4x the CPU when split over two replicas.

## Where the time goes (2 replicas, replica 1; replica 2 is the same)

Self time in the late window, against the early one:

| function | early | late |
|---|---|---|
| `createDeleteSetFromStructStore` (inner loop, `yjs.mjs:216`) | 6.5 s | **42.2 s** |
| `readAndApplyDeleteSet` | 3.9 s | **28.0 s** |
| `writeDeleteSet` | 0.7 s | 2.5 s |
| everything else (socket writes, ioredis, encoders) | flat | flat |

The stacks lead from `Redis.handleIncomingMessage` (the extension's receive path), through `MessageReceiver.apply` and `readSyncStep1`. In the one-replica runs these functions are not in the top of the profile at all; there the time is socket writes (`writev`), the fan-out to editors.

## Why it grows: a measurement of the call itself

`encodeStateAsUpdate(doc, stateVectorOfAnIdenticalPeer)`, on a document made with the load test's edit mix (90% random insert, 10% random delete), in Node on this machine:

| edits so far | characters | delete-set ranges | reply (bytes) | ms per reply |
|---|---|---|---|---|
| 1,000 | 842 | 75 | 210 | 0.18 |
| 5,000 | 4,004 | 414 | 1,222 | 0.47 |
| 15,000 | 11,944 | 1,220 | 3,638 | 1.35 |
| 30,000 | 23,936 | 2,400 | 7,449 | 2.93 |
| 130,000 | 103,764 | 10,459 | 38,362 | 11.6 |

Linear in the edit history, and the peer needs nothing from it: the whole reply is the delete set. A replica sends one SyncStep1 per event-loop turn that had a change, so with about 110 edits a second per replica, each answering and applying a reply of 3 ms or more for each of them, the cost is more than half a core by the end of the run, which is what was measured.

## Other findings

- **Not the Hocuspocus version.** 4.8.0 (current) has the same `onChange` → SyncStep1 path as 4.7.1. The extension's own source comment calls the per-change cost "O(document)" and coalesces within a turn, which is what we see; it does not avoid it.
- **Not the project's code.** `touchedFileIds`, the lock check, `beforeHandleMessage` and the persistence hooks do not show in the top of any profile.
- **One replica is healthy.** 217 edits a second on one replica: p95 about 7 to 8 ms, flat, 25% busy. The roadmap target (p95 < 200 ms) is met by a wide margin in that shape; two replicas meet it too (p95 38.8 ms overall) but would not in a longer session or a busier room.
- **Document size matters less than it looked.** The one-room run has 23,000 characters at the end and p50 stayed flat.

## What is realistic and what is not

The load test's 10% random deletes build a delete set quickly: 2,400 ranges after 30,000 edits. Real typing deletes too (backspace, replace), and a long session in one room accumulates the same way, only slower. It is a real cost, not just an artefact, but this test overstates how fast it grows.

## Decision this feeds

Fix it in how the replicas sync, not in the test. Options, cheapest first:

1. **Subclass the extension: publish the update, not the state vector.** `onChange` already has the update that was just made; publish it as a Yjs update message (applied on the peers with the `redis` origin, so it is not echoed), coalescing a turn's updates with `Y.mergeUpdates`. Keep the SyncStep1 for what it is good at: when a document is loaded, and once in a while (for example every 30 s per active document) as a repair for a missed message, since pub/sub does not guarantee delivery. Cost per edit becomes the size of the edit. Everything else the extension does (initial sync, awareness, stateless messages, store locks) stays as it is.
2. A custom extension from scratch: more code, no benefit over 1.
3. Run one collab replica and scale up before out: at 217 edits a second one replica is 25% busy, so this is the cheap answer for an Evaluation-1 demo. It does not remove the problem, and two replicas are the point of P2-11 to P2-13.

After the fix: re-run the 10-minute 2-replica test, and the kill-a-replica test (P2-16), since a missed update must be repaired by the periodic sync.

## Still open

- **Memory** is still not shown flat. One room did level off (x1.02). Five rooms on one replica still rose x1.20 over ten minutes (130 to 181 MB), as before. A 30 to 60 minute soak with heap snapshots is the way to settle it; do it after the sync fix, since the delete-set work allocates a lot.
- **Compaction** (the worker, every 10 s here) ran during all the runs and did not show in the collab profile.

## How it was run

Collab in Docker with `NODE_OPTIONS=--inspect=0.0.0.0:9229`, the port published to localhost; a small script drove `Profiler.start` and `Profiler.stop` over the DevTools protocol at set times and wrote each window as a `.cpuprofile`; another summed self and inclusive time per function and diffed the windows. Generators ran at below-normal priority. The runs reached convergence with 0 lost edits and 0 divergence in all cases. The scripts and raw profiles are in the session's scratch folder, not in the repository.
