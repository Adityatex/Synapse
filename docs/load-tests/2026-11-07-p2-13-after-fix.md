## What is still open

- **Latency still rises a little**: p95 8 -> 17 ms over ten minutes, p50 flat (3.5 -> 4.2). This is the document growing to about 23,000 characters under random-position inserts, plus the compaction running every 10 s here. It is not the earlier behaviour (a 7x rise with p50 x5, and the CPU doubling), but a longer run is the way to see whether it levels off.
- **Memory is not shown flat.** x1.21 on the worst replica (first quarter of the samples against the last, as the tool defines it). Same as the single-replica runs, so it is not the sync change. The 30 to 60 minute soak with heap snapshots is still the way to settle it.
- **A first attempt at this run was cut off** at about 4 minutes by something outside the tool (exit code 15, no result; the containers stayed up). It is not counted. Up to then it had shown p95 4 to 10 ms, flat.
- **Not staging.** Same caveats as the first run: one laptop, localhost, generators on the same machine.
- **The lost-message repair was tested in `redisSync.test.ts` (dropping a replica's subscription), not under load.** P2-16's kill-a-replica rehearsal is the load-shaped check of it.
